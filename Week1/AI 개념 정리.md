## 1. System Prompt (시스템 프롬프트)

### 정의

LLM에게 역할·규칙·맥락을 **사전에 설정하는 숨겨진 지시문**. 사용자 대화가 시작되기 전에 실행되며, 모델의 동작 방식을 제어한다.

### 장점

- 일관된 톤·역할을 유지할 수 있다
- 코드 배포 없이 즉시 동작 변경 가능
- 보안 경계·응답 형식을 쉽게 설정

### 단점

- 토큰을 소비해 실제 대화에 쓸 컨텍스트가 줄어든다
- 프롬프트 인젝션 공격에 취약하다
- 복잡한 비즈니스 로직을 담기엔 한계가 있다

### 활용법

- 챗봇 페르소나 설정 ("너는 친절한 CS 상담원이야")
- API 서비스 제약 규칙 삽입
- 다국어·형식 응답 지정

### 핵심 포인트

> 모델 자체는 건드리지 않고 **동작만 조정**하는 가장 빠른 방법. 하지만 모델이 완전히 무시할 수도 있다.
> 

<aside>

⭐**정리**⭐

시스템 프롬프트는 대화 할때마다 매번 묶여서 전달되는 내용 

대화할때마다 항상 포함되는 컨텍스트

</aside>

## 2. LLM (Large Language Model)

### 정의

대규모 텍스트 데이터로 **사전학습된 거대 언어모델**. GPT-4, Claude, Gemini, Llama 등이 해당된다. 나머지 모든 개념의 기반이 된다.

### 장점

- 범용적 언어 이해·생성 능력
- 별도 학습 없이 제로샷 추론 가능
- 방대한 세상 지식이 내재화되어 있음

### 단점

- 할루시네이션(사실처럼 보이는 거짓 정보) 발생
- 학습 데이터 이후의 정보를 모른다 (지식 컷오프)
- 추론 비용이 높다

### 활용법

- 텍스트 생성, 번역, 요약
- 코드 작성·리뷰
- 질의응답, 분류, 분석

### 핵심 포인트

> **모든 AI 애플리케이션의 엔진**. 나머지 13개 개념은 모두 이 위에 쌓인다.
> 

<aside>

⭐**정리**⭐

**제로샷** 

- 예시를 하나도 안 줘도 알아서 하는 것, 사전 학습 덕분에 가능하다.

**지식 컷오프** 

- LLM이 학습을 멈춘 날짜, Claude Sonnet 4.6는 **2025년 8월** 이후는 웹검색으로!
- 컷오프 이후 정보가 필요할 때
    - 파인튜닝  →  재학습 필요 (비용·시간 큼)
    - RAG      →  실시간으로 검색해서 컨텍스트에 주입 (빠름)
</aside>

## 3. Prompt Engineering (프롬프트 엔지니어링)

### 정의

모델의 가중치를 건드리지 않고 **입력 방식만 조작**해 최적의 출력을 끌어내는 기술. Chain-of-Thought, Few-shot, Role prompting 등이 대표 기법이다.

### 장점

- 모델 변경 없이 성능 개선 가능
- 비용이 거의 들지 않음
- 빠른 실험·반복이 가능

### 단점

- 모델 버전이 바뀌면 재작업이 필요하다
- 근본적인 한계는 모델 능력에 달려 있다
- 재현성이 낮고 유지보수가 어렵다

### 주요 기법

- **Chain-of-Thought (CoT):** "단계별로 생각해봐"라고 지시해 추론 성능 향상
- **Few-shot:** 예시 2~5개를 같이 넣어 패턴을 학습시킴
- **Role Prompting:** "너는 전문 법률가야"처럼 역할 부여

### 핵심 포인트

> 코드나 데이터 없이 **말만으로 모델을 조종**하는 기술. 비개발자도 할 수 있다.
> 

<aside>

⭐**정리**⭐

**프롬프트** = LLM에게 보내는 입력 텍스트 전부

- LLM한테 하는 말

**프롬프트 잘 쓰려면? ⇒ 대화하듯이 점점 다듬기**

1. 구체적으로 써라

2. 역할을 줘라 (Role Prompting)

3. 출력 형식을 지정해라

4. 예시를 보여줘라 (Few-shot)

5. 단계별로 생각하게 해라 (CoT)

좋은 프롬프트 = 역할 + 맥락 + 구체적 요청 + 출력 형식

```cpp
"너는 UX 라이터야.           ← 역할
앱 온보딩 화면인데           ← 맥락
처음 쓰는 사용자가 버튼을
누르도록 유도하는 문구를     ← 구체적 요청
3가지 버전으로 써줘"         ← 출력 형식
```

</aside>

## 4. Fine-Tuning (파인튜닝)

### 정의

사전학습된 LLM을 **특정 도메인 데이터로 추가 학습**시켜 전문화하는 과정. 모델의 가중치 자체가 변경된다.

### 장점

- 도메인 특화 성능을 극대화할 수 있다
- 추론 시 긴 프롬프트가 필요 없어 비용 절감
- 특정 말투·스타일을 일관되게 학습

### 단점

- 학습 데이터 확보가 어렵고 비용이 크다
- Catastrophic Forgetting: 새 지식을 학습하면서 기존 지식을 잊을 수 있다
- 데이터가 변경되면 재학습이 필요하다

### 주요 방법

- **SFT (Supervised Fine-Tuning):** 레이블된 데이터로 직접 학습
- **LoRA:** 가중치 일부만 학습해 효율적으로 파인튜닝
- **RLHF:** 인간 피드백으로 강화학습 (ChatGPT 방식)
- **GRPO:** 인간 피드백 없이 강화학습, 모델이 스스로 점수매긴다.

```cpp
RLHF   →  인간이 채점하니 비싸고 느림
           근데 "좋은 글" 같은 주관적인 것도 학습 가능

**딥시크** →  자동 채점이니 빠르고 저렴
           근데 정답이 명확한 것만 가능 (수학, 코딩)
           "이 글이 감동적이야" 같은 건 채점 불가
```

### 핵심 포인트

> 프롬프트로 안 되는 것을 **모델 자체를 바꿔서 해결**. 하지만 비용과 시간이 크다.
> 

<aside>

⭐**정리**⭐

**파인튜닝** 

- 소넷, 하이쿠, 오퍼스 처럼 모델을 만드는 것, 완전 기본 모델(Qwen 등)에 가중치를 적용해서 나만의 모델을 만드는 것
</aside>

## 5. Context Engineering (컨텍스트 엔지니어링)

### 정의

시스템 프롬프트·문서·메모리·도구 출력 등 **컨텍스트 윈도우 전체를 설계**하는 고급 기술. 프롬프트 엔지니어링의 상위 개념으로, "무엇을 말하느냐"가 아니라 "컨텍스트를 어떻게 구성하느냐"에 집중한다.

### 장점

- 복잡한 에이전트 시스템에서 필수적
- 동적으로 정보를 주입할 수 있다
- 성능과 비용을 동시에 최적화 가능

### 단점

- 설계 난이도가 높다
- 컨텍스트 길이 제한이 존재한다
- 오케스트레이션 로직이 복잡해진다

### 활용법

- 멀티스텝 에이전트 파이프라인 설계
- RAG에서 어떤 문서를 어떻게 넣을지 결정
- 대화 히스토리·메모리 관리

### 핵심 포인트

> Prompt Engineering이 "문장 쓰기"라면, Context Engineering은 **"공간 설계"**. 에이전트 시대의 핵심 역량.
> 

<aside>

⭐**정리**⭐

**오케스트레이션**

- 여러 에이전트·툴·스킬을 지휘하는 것
</aside>

## 6. Skill (스킬)

### 정의

에이전트가 수행할 수 있는 **특정 능력의 단위**. 함수·API 호출·서브워크플로우 형태로 캡슐화된 재사용 가능한 능력.

### 장점

- 재사용 가능한 모듈화
- 독립적으로 테스트·유지보수 가능
- 조합으로 복잡한 작업을 수행

### 단점

- 상황에 맞는 스킬 선택 로직이 필요
- 스킬이 많아질수록 관리 복잡도 증가
- 스킬 간 충돌 가능성

### 활용법

- 파일 읽기/쓰기 스킬
- 웹 검색 스킬
- 코드 실행 스킬
- 이메일 발송 스킬

### 핵심 포인트

> 에이전트의 **팔다리**. 스킬이 많을수록 할 수 있는 일이 늘어난다.
> 

<aside>

⭐**정리**⭐

[**claude.md**](claude.md)

- 이 프로젝트가 뭔지 Claude한테 설명하는 문서
- 항상 읽힘 (시스템 프롬프트)

**스킬 ([SKILL.md](http://skill.md/))**

- 이 작업을 할 때는 이렇게 해라"는 레시피
- 필요할 때만 읽힘 (Context Engineering)

**에이전트** 

- 스스로 판단하고 행동하는 주체
- 자율성이 있다.
- 사람이다.

```cpp
claude.md  →  배경지식 주입 (문서)
스킬       →  작업 방법 주입 (레시피)
에이전트   →  스스로 생각하고 실행 (요리사)
```

</aside>

## 7. Harness Engineering (하네스 엔지니어링)

### 정의

에이전트 시스템을 **제어·관찰·평가하기 위한 인프라 설계**. 테스트 환경, 모니터링, 실행 컨테이너, 평가 자동화를 포함한다.

### 장점

- 안전한 실행 환경 보장
- 성능 측정·디버깅 가능
- 자동화 테스트 지원

### 단점

- 초기 구축 비용이 크다
- 운영 복잡도 증가
- 범용 표준 솔루션이 부족하다

### 활용법

- 에이전트 벤치마킹 자동화
- CI/CD 파이프라인에 에이전트 테스트 통합
- 실행 샌드박스 환경 구성

### 핵심 포인트

> 자동차의 **섀시**. 엔진(LLM)이 아무리 좋아도 감싸는 구조가 없으면 안전하게 달릴 수 없다.
>

## 8. Hook (훅)

### 정의

에이전트 실행 흐름 중 **특정 시점에 끼어드는 콜백 메커니즘**. 전처리·후처리·로깅·검증 등 비침투적으로 기능을 추가한다.

### 장점

- 원본 코드 변경 없이 기능 추가 (비침투적)
- 실행 흐름을 가로채어 제어 가능
- 관심사 분리 (로깅·검증·비용 추적을 분리)

### 단점

- 훅이 많아지면 실행 흐름 파악이 어렵다
- 훅 간 순서·충돌 관리가 필요하다

### 활용법

- 입력 검증 훅 (위험한 입력 차단)
- 응답 로깅 훅 (모든 응답 기록)
- 비용 추적 훅 (토큰 사용량 집계)
- 안전 필터 훅 (부적절한 응답 차단)

### 핵심 포인트

> 파이프라인 중간에 껴넣는 **플러그인**. WordPress 훅이나 React 훅과 같은 개념.
> 

<aside>

⭐**정리**⭐

**하네스 엔지니어링**

- 시스템 프롬프트, 도구 설정, 가드레일, 오케스트레이션 로직 등 모델을 감싸는 전체 구조르르 설계하는 것
- 모델이 동작하는 전체 틀을 짜는 것

**훅**

- 특정 시점에 개입
- 모델이 특정 행동을 할때 자동으로 개입하는 구조
</aside>

## 9. Hermes Agent (헤르메스 에이전트)

### 정의

"기억하는 챗봇"이 아니라, **장기 실행을 전제로 설계된 에이전트 플랫폼**.
스킬 시스템, 세션 검색, 메시징 게이트웨이, 크론 자동화, 다중 실행 환경을 포함한다.
Nous Research가 만든 오픈소스 프로젝트로, 슬로건은 **"The agent that grows with you"**.

### 장점

- 반복 작업 패턴을 스킬로 자동 학습해서 다음엔 더 빠르게 처리
- 세션이 끊겨도 기억(메모리)이 유지됨
- Telegram·Discord·Slack 등 15개 이상 메시징 플랫폼 연결 가능
- 24/7 자율 실행 (cron 스케줄러)
- 병렬 서브에이전트로 여러 작업 동시 처리

### 단점

- 같은 작업을 10~20회 이상 반복해야 학습 효과가 체감됨
- API 호출당 73%가 고정 오버헤드 (토큰 비용 높음)
- IDE 통합 없음 (VS Code 인라인 지원 안 됨)
- Windows 네이티브 미지원 (WSL2로 우회 가능)

### 활용법

- VPS에 올려두고 Telegram으로 원격 제어하는 개인 비서
- 반복 업무 자동화 (매일 보고서 생성, 모니터링)
- 멀티에이전트 오케스트레이터
- OpenClaw에서 마이그레이션

### 핵심 포인트

> 자가학습의 실체는 파인튜닝이 아니다.
반복 작업 경험을 **마크다운 스킬 파일로 저장**하고, 다음 요청 시 **컨텍스트에 주입**하는 방식이다. = 스킬 + 컨텍스트 엔지니어링의 조합.
> 

---

## 10. RAG (Retrieval-Augmented Generation)

### 정의

외부 지식베이스에서 **관련 문서를 검색(Retrieve)해 LLM의 컨텍스트에 주입**하고 답변을 생성(Generate)하는 패턴. 벡터 DB와 임베딩을 활용한다.

### 장점

- 학습 데이터 이후의 최신 정보를 활용 가능
- 할루시네이션 감소 (출처 기반 응답)
- 파인튜닝 없이 도메인 지식 추가

### 단점

- 검색 품질에 전체 성능이 의존한다
- 레이턴시가 증가한다
- 벡터 DB 구축·관리 비용이 든다

### 주요 구성 요소

- **청킹(Chunking):** 문서를 적절한 크기로 쪼개기
- **임베딩(Embedding):** 텍스트를 벡터로 변환
- **벡터 DB:** 임베딩 저장 및 유사도 검색

### 활용법

- 사내 문서 QA 시스템
- 최신 뉴스 기반 요약
- 법률·의료 검색 보조

### 핵심 포인트

> 모델에 **외장 하드**를 달아준 것. 모르는 것을 실시간으로 찾아서 답변.
> 

<aside>

⭐**정리**⭐

**벡터 DB**

- 텍스트, 이미지 등을 숫자 배열(벡터)로 변환해서 저장하고, 의미적으로 유사한 것을 빠르게 찾아주는 데이터 베이스
- 벡터들 사이의 거리를 꼐산해서 의미가 가까운 데이터를 검색한다.
</aside>

## 11. Agentic-RAG (에이전틱 RAG)

### 정의

RAG의 검색 과정을 **에이전트가 자율적으로 판단하고 반복 수행**하는 고급 패턴. 쿼리 재작성, 다중 검색, 검색 전략 선택 등을 스스로 결정한다.

### RAG와의 차이

|  | RAG | Agentic-RAG |
| --- | --- | --- |
| 검색 횟수 | 1회 고정 | 필요에 따라 반복 |
| 쿼리 전략 | 정적 | 동적으로 재작성 |
| 복잡도 | 중간 | 높음 |
| 정확도 | 좋음 | 더 좋음 |

### 장점

- 복잡한 다단계 질문 처리 가능
- 검색 전략을 동적으로 조정
- 일반 RAG보다 높은 정확도

### 단점

- 구현이 복잡하다
- 비용과 시간이 증가한다
- 실행 경로가 예측 불가능할 수 있다

### 활용법

- 복잡한 연구 보조 ("이 주제에 대해 여러 관점에서 조사해줘")
- 다단계 법률 문서 분석
- 실시간 정보 합성

### 핵심 포인트

> RAG에 **자율성을 부여**한 것. "찾아줘"가 아니라 스스로 찾는 방법을 결정한다.
>

## 12. Tool / Function Calling (툴)

### 정의

LLM이 **외부 함수·API를 호출**할 수 있도록 하는 메커니즘. LLM이 텍스트만 생성하는 것을 넘어 실제 세계에 행동할 수 있게 만든다.

### 장점

- 계산기·검색·DB 등 실제 행동 가능
- 최신 정보에 접근 가능
- 수학 계산 등 정확도 향상

### 단점

- 툴 정의 자체도 토큰을 소비한다
- 잘못된 툴을 선택할 수 있다
- API 호출 권한 등 보안 리스크 존재

### 활용법

- 날씨 API 호출
- 코드 실행 (Python 인터프리터)
- 이메일·캘린더 제어
- 데이터베이스 쿼리

### 핵심 포인트

> LLM을 **읽기 전용**에서 **행동 가능한 에이전트**로 바꿔주는 열쇠.
> 

<aside>

⭐**정리**⭐

**Tool**

- API, 모델을 호출할 수 있는 모든 기능
- Claude Code에서 `p4` 명령어 치는 것도 결국 터미널 실행 툴
- Agent가 판단해서 Tool을 실행한다.
</aside>

## 13. MCP (Model Context Protocol)

### 정의

AI 모델과 외부 도구·데이터 소스 간의 **표준화된 통신 프로토콜**. Anthropic이 제안한 오픈 표준으로, USB처럼 모델과 툴을 표준 방식으로 연결한다.

### Tool과의 차이

|  | Tool (Function Calling) | MCP |
| --- | --- | --- |
| 표준화 | 모델마다 다름 | 범용 표준 |
| 재사용성 | 낮음 | 높음 |
| 구현 위치 | 모델 내 정의 | 독립 서버 |
| 생태계 | 파편화 | 통합 |

### 장점

- 툴 생태계 표준화 (한 번 만들면 어느 모델에서도 사용)
- 재사용 가능한 MCP 서버 생태계
- 모델과 독립적으로 툴 관리 가능

### 단점

- MCP 서버 구현이 필요하다
- 보안 모델이 아직 성숙하지 않음

### 활용법

- Claude + 외부 툴 연결 (Gmail, Slack, GitHub 등)
- 여러 모델이 동일한 툴 서버 공유
- IDE 통합 (Claude Code)

### 핵심 포인트

> 툴을 모델에 종속시키지 않고 **표준 규약으로 아무 모델에나 꽂을 수 있게**. AI 세계의 USB-C.
>
